## What this project is

SquadPulse is a Hebrew-first (RTL) web platform for adult football clubs to manage squad, tactics, training, and match data from one place. Multi-club from day one, fully isolated per club. It's also a deliberate exercise in professional engineering practice: real Git workflow, Jira-driven planning, security, testing, and deployment — done properly, not skipped because it's a side project.

**Status:** Phase 2 (backend core) in progress. The first real endpoints exist — auth: `/auth/login`, `/auth/refresh`, `/auth/logout`, `/auth/forgot-password`, `/auth/reset-password`, `/auth/users/invite`, `/auth/users/{id}/permission-level` (see README "Auth API"). Squad (KAN-26): `GET /squad/players` (filters), `GET /squad/players/{id}`, `POST /squad/players`, `PUT /squad/players/{id}`; KAN-27: `POST /squad/players/{id}/release`, `POST /squad/players/{id}/reactivate`, `DELETE /squad/players/{id}` (ADMIN); KAN-28: `GET /squad/summary`; KAN-29: `PUT`/`GET`/`DELETE /squad/players/{id}/photo` and `hasPhoto` on player responses (see README "Squad API"). No other feature code has shipped yet; frontend and scraper are still skeletons.

## Standing rules — always follow these

1. **Ask before doing.** Before making a change with real consequences — creating/editing Jira issues, pushing commits, opening PRs, touching CI/deploy config, deleting anything — explain what you're about to do and wait for confirmation. Don't chain multiple actions without checking in. This applies until Gal says otherwise.
2. **English in code, Hebrew in product.** All code, comments, commit messages, branch names, Jira issues, and docs (including this file and `docs/spec.md`) are in English. The end-user-facing UI is in Hebrew. Never mix these up.
3. **Exception — football terms stay in English in the UI too.** Position codes (`GK`, `CB`, `DM`, ...) and formation notation (`4-3-3`) are shown as-is in English even in the Hebrew UI — see spec section 01. Don't "fix" this by translating them.
4. **`clubId` isolation is the most safety-critical thing in this codebase.** Every query that touches tenant data must go through the central `clubId`-filtering layer in the `common` module (see spec section 03). Any PR touching data access should be checked against this specifically. Custom repository methods must include `ClubId` in their name (ArchUnit-enforced); the sole escape hatch is `@GloballyScoped`, for lookups by a globally unique value with no club context yet (e.g. `UserRepository.findByEmail` at login) — rare, and each use reviewed individually. For HTTP requests `ClubContext` is populated only by `auth.JwtAuthenticationFilter`, from the access token's `clubId` claim — never accept a clubId from a request body, path or query parameter. Likewise, every repository's entity must extend `ClubScopedEntity` or be explicitly `@NotClubScoped` (the app won't start otherwise); `@NotClubScoped` is only for data no club owns — today just `Club`, the tenant root.
5. **Nothing secret goes into git.** Passwords, the Argon2id pepper, API keys, tokens — env vars / secrets manager only. Never commit them, never hardcode them, never put them in Jira or docs either.
6. **i18n from day one.** All UI strings go through the i18n library, never hardcoded into components, even though there's currently only one supported language (Hebrew).
7. **Keep the docs in sync, in the same commit.** When a change affects architecture, module structure, setup/run steps, tooling or dependency versions, or conventions, update `README.md` and this file in that same commit — and re-check them against the change before committing. `docs/spec.md` is Gal's design document: never edit it on your own initiative. ## Architecture at a glance

Modular monolith (Spring Boot), not microservices — see spec section 02 for the reasoning and when a split would actually be reconsidered.

```
squadpulse/
├── backend/                          # Spring Boot monolith
│   └── src/main/java/com/squadpulse/
│       ├── auth/                     # JWT, RBAC, users
│       ├── squad/                    # Players, roster
│       ├── tactics/                  # Tactical board (Canvas backend)
│       ├── training/                 # Training calendar & sessions
│       ├── match/                    # League table, fixtures, lineups (domain data)
│       ├── scrapingintegration/      # Talks to the scraper worker, feeds match
│       └── common/                   # Shared: clubId enforcement, error handling, etc.
├── frontend/                         # React 19 + TypeScript + Vite + Tailwind
├── scraper/                          # Node.js worker (Playwright/Cheerio)
├── docker-compose.yml                # MongoDB (single-node replica set) + Redis, local dev only
├── docs/spec.md                      # Full technical & product spec
├── docs/agent-prompts/               # Per-ticket implementation prompts (KAN-xx-prompt.md)
└── CLAUDE.md                         # This file
```

Tech stack: React 19 / TS / Vite / Tailwind / shadcn/ui / TanStack Query / Zustand / Konva.js / Recharts on the frontend; Java + Spring Boot on the backend; MongoDB + Redis for storage; Node.js (Playwright/Cheerio) for the scraper; stateless JWT auth via Spring Security (HS256 Access token in the `Authorization` header + opaque, rotating Refresh token in an HttpOnly cookie, tracked in Redis) with Argon2id + pepper for passwords; GitHub Actions for CI.

Access control: every endpoint requires a valid access token unless `auth.SecurityConfig` lists it as public. Permission levels are Spring Security authorities of the same name — use `@PreAuthorize("hasAuthority('ADMIN')")` on controller methods, never manual permission checks in controller bodies. The levels form a hierarchy, `ADMIN > EDIT_FULL > EDIT_PARTIAL > VIEW_ONLY` (a `RoleHierarchy` bean in `auth.SecurityConfig`, derived from `PermissionLevel`'s declaration order — so that order is meaningful), so require the **lowest** level that may use an endpoint; read endpoints require `VIEW_ONLY` explicitly. Every request handler must declare who may call it — `@PreAuthorize` (on the method or its class) or, for the rare endpoint that works without an access token, `@common.PublicEndpoint` plus an entry in `SecurityConfig.PUBLIC_ENDPOINTS` (ArchUnit-enforced, and a test checks the two agree). `EDIT_PARTIAL` is assignable but currently required by no endpoint (so today it grants what `VIEW_ONLY` does) — its meaning gets defined with the feature endpoints. Errors go through `common.GlobalExceptionHandler`; module-specific 401s extend `common.UnauthorizedException` (likewise 409 → `common.ConflictException`, 429 → `common.TooManyRequestsException`, a 400 that Bean Validation can't express, e.g. `minAge > maxAge` → `common.BadRequestException`, given a field name when one field is to blame). Validation 400s put one `"name: message"` entry per invalid field or query parameter in `details`: body constraints (`MethodArgumentNotValidException`), `@RequestParam` constraints (Spring's built-in method validation → `HandlerMethodValidationException` — so don't put `@Validated` on a controller, which would switch to an unmapped `ConstraintViolationException`), unconvertible parameters (`MethodArgumentTypeMismatchException`) and a field-scoped `BadRequestException`. A body value Jackson can't bind (a `tools.jackson.databind.DatabindException` with a path) gives `"<path>: invalid value"`; rejected values are never echoed. Standard Spring MVC client errors are mapped explicitly (KAN-31): an unsupported or unparseable `Content-Type` → 415 (`details` and the `Accept` header list the accepted types), an `Accept` the endpoint can't satisfy → 406 (always answered as JSON), a missing required query parameter / header / cookie → 400 `"<name>: is required"`. Messages never echo client input — Spring's own messages often do, so handlers write fixed texts (a listed type comes from the server, never from the request). Any other exception reaches `handleUnexpected`, which answers a Spring `org.springframework.web.ErrorResponse` (`ResponseStatusException`, an unmapped `ServletRequestBindingException`, ...) with **its** status and headers under a fixed message, and anything else with the generic 500. Logging: every 500 (and any 5xx `ErrorResponse`) is logged at ERROR with the stack trace plus the request's method and path — never its query string, headers, body or cookies; a 4xx is never logged at ERROR (the 409 optimistic-lock WARN stays); a client that disconnected mid-response (Spring's `DisconnectedClientHelper`, e.g. Tomcat's `ClientAbortException`) is logged at DEBUG only, and nothing is written to it or to any already-committed response. Error responses built by the newer handlers set `Content-Type: application/json` explicitly, so Spring doesn't negotiate them against `Accept`. Exceptions thrown in a servlet filter never reach the advice: Spring Boot's `/error` renders them in its own shape (`timestamp`, `status`, `error`, `path`), logged by Tomcat — a known gap. Controller tests outside `auth` get the real security chain from `auth.AuthWebMvcTestConfig` and tokens from `auth.TestAccessTokens` (both test code). Code that runs without a club context but must write club-scoped data (e.g. a public endpoint acting on a user it looked up) uses `ClubContext.callAs(clubId, ...)` with a clubId from a stored record, never from the request.

`User` uses optimistic locking (`@Version`, KAN-24): saving a stale copy throws `OptimisticLockingFailureException` instead of overwriting a concurrent write. So any code that loads, changes and saves a `User` must handle that: reload and retry (`auth.UserWriteRetry`) for an absolute change to fields no other writer touches ("set the level to X"), re-checking anything the change depends on (e.g. `active`) on every attempt; otherwise let it become a 409 (`common.GlobalExceptionHandler`), e.g. for a multi-field edit based on what the admin saw. A future deactivation endpoint must follow this pattern. User documents stored before that are given a version at startup by `auth.UserVersionBackfill` — the one direct `MongoOperations` write outside `common`, allowed because it's a schema backfill that reads and returns no tenant data; don't take it as precedent.

`squad.Player` is a club-scoped roster record, not a global person: the same person in two clubs is two independent records, with no cross-club link and no `@GloballyScoped` lookup. Leaving the club is a soft delete (`active = false`). It's versioned with `@Version` from day one, like `User` (new collection, so no backfill). Jersey numbers are unique among a club's active players via a partial unique index (`Player.JERSEY_NUMBER_INDEX`, filter: `jerseyNumber` is a number and `active` is true) — the index is the guarantee, not a service-level check. Bean Validation on entities (`Player`, `User`) is **not** run on save; only request DTOs are validated, so a write path must validate its input before building the entity. The secondary-≠-primary position rule is `squad.DistinctPositions`, usable on any `squad.HasPositions` (e.g. a request record). The squad API (`squad.PlayerService`) loads a player through the club-scoped `findById` first (another club's → 404), filters lists in memory (never a hand-built `MongoTemplate` query, which would bypass club scoping), maps a `DuplicateKeyException` to a jersey 409 only if its `MongoWriteException` cause names `Player.JERSEY_NUMBER_INDEX` (anything else is rethrown), and on `PUT` compares the client's `version` to the stored one; a mismatch and a save race lost after that check are the same `StalePlayerVersionException` 409 (no retry — it's a multi-field form edit). A released player is read-only until re-activated; re-activation sets the jersey number from its request (null = none, index-checked, no fallback), the only way to change a released player's number. Permanent delete (ADMIN) is deliberately not version-checked — `ClubScopedRepositoryImpl.delete` removes by id + clubId only. Player ages use `Clock.systemDefaultZone()`, the zone of Hibernate Validator's default `ClockProvider` that `@AdultAge` uses. Ages are computed only by `PlayerService.completedYears` (whole years, `Period`) and `PlayerService.exactAge` (fractional, for the summary's average; its whole part is always `completedYears`, so a 29 February birthday falls on 1 March in a non-leap year). `Position.line()` is the only place that maps a position to its `Line`; don't hard-code that mapping anywhere else.

Images (player photos; the club logo, KAN-30, will reuse this) go only through `common.ImageStorage` — no method takes a `clubId`, it's read from `ClubContext`. Its only implementation, `common.GridFsImageStorage` (GridFS bucket `images`), is the only GridFS code in the codebase (ArchUnit-enforced: nothing outside `common` may depend on GridFS) and applies the `clubId` itself: every query is built by one helper that adds `metadata.clubId`, since GridFS is a documented bypass of the club-scoped repository layer. Keep the interface free of GridFS / driver types so it can move to S3/R2. Uploads go through `common.ImageValidator` → a `common.ValidatedImage`: the type comes from magic bytes only (JPEG/PNG/WebP, `common.ImageType.detect`), never from the client's `Content-Type` or filename; empty or wrong type → field-scoped `BadRequestException` on `file`, over `squadpulse.images.max-size` (2 MB) → `common.PayloadTooLargeException` (413; the container's `MaxUploadSizeExceededException` gives the same 413). `server.tomcat.max-swallow-size: 20MB` is deliberate and server-wide: it makes an oversize upload get its 413 instead of a connection reset, at the cost that Tomcat may read up to 20MB of any rejected body. A reverse proxy in front of the app (Phase 6) must allow request bodies of at least 3MB (nginx defaults to 1MB) — see README "Deployment notes". Replace semantics: an owner's current image is the latest by `(uploadDate, _id)`; `store` uploads first, then deletes only that owner's files strictly *before* the new one — never "all but mine" — so concurrent uploads leave one, with no transaction. The photo isn't on the `Player` document (no `version` change). `PlayerService.delete` removes the photo **before** the player, so a failure in between leaves a photo-less player that a retry cleans up, never an unreachable orphan file; an upload re-checks that the player still exists after storing and removes its file if not.

Email goes through `common.EmailSender`. Its only implementation, `common.LoggingEmailSender`, logs activation / reset codes in plaintext — local development only; it must be replaced by a real, asynchronous provider before any deployment (Phase 6+).
