## Standing rules — always follow these

1. **Ask before doing.** Before making a change with real consequences — creating/editing Jira issues, pushing commits, opening PRs, touching CI/deploy config, deleting anything — explain what you're about to do and wait for confirmation. Don't chain multiple actions without checking in. This applies until Gal says otherwise.
2. **English in code, Hebrew in product.** All code, comments, commit messages, branch names, Jira issues, and docs (including this file and `docs/spec.md`) are in English. The end-user-facing UI is in Hebrew. Never mix these up.
3. **Exception — football terms stay in English in the UI too.** Position codes (`GK`, `CB`, `DM`, ...) and formation notation (`4-3-3`) are shown as-is in English even in the Hebrew UI — see spec section 01. Don't "fix" this by translating them.
4. **`clubId` isolation is the most safety-critical thing in this codebase.** Every query that touches tenant data must go through the central `clubId`-filtering layer in the `common` module (see spec section 03). Any PR touching data access should be checked against this specifically. Custom repository methods must include `ClubId` in their name (ArchUnit-enforced); the sole escape hatch is `@GloballyScoped`, for lookups by a globally unique value with no club context yet (e.g. `UserRepository.findByEmail` at login) — rare, and each use reviewed individually. For HTTP requests `ClubContext` is populated only by `auth.JwtAuthenticationFilter`, from the access token's `clubId` claim — never accept a clubId from a request body, path or query parameter. Likewise, every repository's entity must extend `ClubScopedEntity` or be explicitly `@NotClubScoped` (the app won't start otherwise); `@NotClubScoped` is only for data no club owns — today just `Club`, the tenant root.
5. **Nothing secret goes into git.** Passwords, the Argon2id pepper, API keys, tokens — env vars / secrets manager only. Never commit them, never hardcode them, never put them in Jira or docs either.
6. **i18n from day one.** All UI strings go through the i18n library, never hardcoded into components, even though there's currently only one supported language (Hebrew).
7. **Keep the docs in sync, in the same commit.** When a change affects architecture, module structure, setup/run steps, tooling or dependency versions, or conventions, update `README.md` and this file in that same commit — and re-check them against the change before committing. `docs/spec.md` is Gal's design document: never edit it on your own initiative. ## Architecture at a glance

Modular monolith (Spring Boot), not microservices — see spec section 02 for the reasoning and when a split would actually be reconsidered.

```
squadpulse/
├── backend/                          # Spring Boot monolith
│   └── src/main/java/com/squadpulse/
│       ├── auth/                     # JWT, RBAC, users
│       ├── squad/                    # Players, roster
│       ├── tactics/                  # Tactical board (Canvas backend)
│       ├── training/                 # Training calendar & sessions
│       ├── match/                    # League table, fixtures, lineups (domain data)
│       ├── scrapingintegration/      # Talks to the scraper worker, feeds match
│       └── common/                   # Shared: clubId enforcement, error handling, etc.
├── frontend/                         # React 19 + TypeScript + Vite + Tailwind
├── scraper/                          # Node.js worker (Playwright/Cheerio)
├── docker-compose.yml                # MongoDB (single-node replica set) + Redis, local dev only
├── docs/spec.md                      # Full technical & product spec
├── docs/agent-prompts/               # Per-ticket implementation prompts (KAN-xx-prompt.md)
├── docs/design/ui-conventions.md     # Approved UI design (KAN-44): tokens, type scale, layout rules
└── CLAUDE.md                         # This file
```

Tech stack: React 19 / TS / Vite / Tailwind 4 / shadcn/ui (Base UI, `rtl: true`) / React Router 8 / TanStack Query / Zustand / Konva.js / Recharts on the frontend; Java + Spring Boot on the backend; MongoDB + Redis for storage; Node.js (Playwright/Cheerio) for the scraper; stateless JWT auth via Spring Security (HS256 Access token in the `Authorization` header + opaque, rotating Refresh token in an HttpOnly cookie, tracked in Redis) with Argon2id + pepper for passwords; GitHub Actions for CI.

Access control: every endpoint requires a valid access token unless `auth.SecurityConfig` lists it as public. Permission levels are Spring Security authorities of the same name — use `@PreAuthorize("hasAuthority('ADMIN')")` on controller methods, never manual permission checks in controller bodies. The levels form a hierarchy, `ADMIN > EDIT_FULL > EDIT_PARTIAL > VIEW_ONLY` (a `RoleHierarchy` bean in `auth.SecurityConfig`, derived from `PermissionLevel`'s declaration order — so that order is meaningful), so require the **lowest** level that may use an endpoint; read endpoints require `VIEW_ONLY` explicitly. Every request handler must declare who may call it — `@PreAuthorize` (on the method or its class) or, for the rare endpoint that works without an access token, `@common.PublicEndpoint` plus an entry in `SecurityConfig.PUBLIC_ENDPOINTS` (ArchUnit-enforced, and a test checks the two agree; the sole exemption is `common.ApiErrorController`, see below). The caller re-check (`auth.ActiveCallerCheck`) is required on exactly these: every user-management write (invite, permission-level, deactivate, reactivate — KAN-37) and `PATCH /clubs/me` (KAN-38) — and on any new endpoint of those two kinds (a user-management write, or a write to the club document's settings). Each re-reads its caller once, before anything else, and answers the generic 401 if they're deactivated or gone, closing the access-token window for a deactivated admin. The club-logo writes (`PUT`/`DELETE /clubs/me/logo`) and the staff-photo writes (`PUT`/`DELETE /users/me/photo` and `/users/{id}/photo`) deliberately don't re-check the caller: they're cosmetic and reversible, and a deactivated user's access token lives at most 15 minutes — accepted, not a gap to fill. (A staff-photo write still checks its *target*: a deactivated user's photo → 409.) Nothing else adds a per-request user lookup (`/auth/users/me` uses the same check). The one place `VIEW_ONLY` writes anything is the caller's own photo (`/users/me/photo`, KAN-32) — their own profile, never another user's or club data. `EDIT_PARTIAL` is assignable but currently required by no endpoint (so today it grants what `VIEW_ONLY` does) — its meaning gets defined with the feature endpoints. Errors go through `common.GlobalExceptionHandler`; module-specific 401s extend `common.UnauthorizedException` (likewise 409 → `common.ConflictException` — every subclass passes a machine-readable code, `ConflictException(CODE, message)`, declared as `static final String CODE` in its own class (UPPER_SNAKE_CASE, checked by the constructor) and sent as the error body's `code` (KAN-50); codes are stable API: add new ones, never rename or reuse one; the generic optimistic-lock 409 is `CONCURRENT_MODIFICATION`; no other status has a code yet, so every other error body has `"code": null` —, 429 → `common.TooManyRequestsException`, a 400 that Bean Validation can't express, e.g. `minAge > maxAge` → `common.BadRequestException`, given a field name when one field is to blame). Validation 400s put one `"name: message"` entry per invalid field or query parameter in `details`: body constraints (`MethodArgumentNotValidException`), `@RequestParam` constraints (Spring's built-in method validation → `HandlerMethodValidationException` — so don't put `@Validated` on a controller, which would switch to an unmapped `ConstraintViolationException`), unconvertible parameters (`MethodArgumentTypeMismatchException`) and a field-scoped `BadRequestException`. A body value Jackson can't bind (a `tools.jackson.databind.DatabindException` with a path) gives `"<path>: invalid value"`; rejected values are never echoed. Standard Spring MVC client errors are mapped explicitly (KAN-31): an unsupported or unparseable `Content-Type` → 415 (`details` and the `Accept` header list the accepted types), an `Accept` the endpoint can't satisfy → 406 (always answered as JSON), a missing required query parameter / header / cookie → 400 `"<name>: is required"`. Rejected values and request headers (e.g. the `Content-Type` sent) are never echoed back — Spring's own messages often do, so handlers write fixed texts (a listed type comes from the server, never from the request); only the 404 for an unknown path and the 405 name the request's method and path. Any other exception reaches `handleUnexpected`, which answers a Spring `org.springframework.web.ErrorResponse` (`ResponseStatusException`, an unmapped `ServletRequestBindingException`, ...) with **its** status and headers under a fixed message, and anything else with the generic 500. Logging: every 500 (and any 5xx `ErrorResponse`) is logged at ERROR with the stack trace plus the request's method and path — never its query string, headers, body or cookies; a 4xx is never logged at ERROR (the 409 optimistic-lock WARN stays); a client that disconnected mid-response (Spring's `DisconnectedClientHelper`, e.g. Tomcat's `ClientAbortException`) is logged at DEBUG only, and nothing is written to it or to any already-committed response. The error body is `common.ApiErrorResponse` `{timestamp, status, error, code, message, details}`; `code` is always written, `null` when absent. Error bodies are always JSON, whatever the request's `Accept` header: every handler builds its response through `GlobalExceptionHandler.respond(...)`, which sets `Content-Type: application/json` explicitly so Spring doesn't negotiate it (otherwise a client accepting only XML got an empty body, or a container 500 for the app's own exceptions) — a new handler must use it too. Errors raised below Spring MVC get the same shape (KAN-35): an exception escaping a servlet filter is caught by `common.UnhandledExceptionFilter` (registered first, before Spring Security's chain; logged once at ERROR with method + path via the shared `common.ErrorLogging`, answered with the generic JSON 500 — Tomcat no longer logs it), and anything that still reaches the container's `/error` (e.g. the security firewall's `sendError(400)` for a `//` path) is rendered by `common.ApiErrorController`, which replaces Boot's `BasicErrorController` (Whitelabel off via `spring.web.error.whitelabel.enabled: false`) with a fixed message and the error's status; a direct `GET /error` is a 401 without a token, a 404 with one. A new filter must not write its own error format — let the exception propagate. A test that asserts on what the whole app logs (the root logger) uses the shared test helper `common.CapturedLogs` (KAN-55), which reads a synchronized snapshot and leaves background driver loggers (`io.netty`, `io.lettuce`: clients of cached test contexts whose containers have stopped) out of its ERROR / WARN checks, by logger name only — never count raw root-logger events. `ApiErrorController` is the one class exempt from the endpoint-authorization ArchUnit rule (by exact class: the error dispatch has no authenticated caller). Only requests Tomcat's connector rejects itself (a malformed request line or header, an encoded `/` in the path) still get Tomcat's HTML page. Controller tests outside `auth` get the real security chain from `auth.AuthWebMvcTestConfig` and tokens from `auth.TestAccessTokens` (both test code). Code that runs without a club context but must write club-scoped data (e.g. a public endpoint acting on a user it looked up) uses `ClubContext.callAs(clubId, ...)` with a clubId from a stored record, never from the request.

`User` uses optimistic locking (`@Version`, KAN-24): saving a stale copy throws `OptimisticLockingFailureException` instead of overwriting a concurrent write. So any code that loads, changes and saves a `User` must handle that: reload and retry (`auth.UserWriteRetry`) for an absolute change to fields no other writer touches ("set the level to X"), re-checking anything the change depends on (e.g. `active`) on every attempt; otherwise let it become a 409 (`common.GlobalExceptionHandler`), e.g. for a multi-field edit based on what the admin saw. Deactivation / re-activation (`auth.UserActivationService`, KAN-37) follows it: absolute, retried, the "already in that state" no-op re-checked per attempt, and `sessionsInvalidatedAt` set from a clock read inside each attempt and never moved backwards. User documents stored before that are given a version at startup by `auth.UserVersionBackfill` — the one direct `MongoOperations` write outside `common`, allowed because it's a schema backfill that reads and returns no tenant data; don't take it as precedent.

`squad.Player` is a club-scoped roster record, not a global person: the same person in two clubs is two independent records, with no cross-club link and no `@GloballyScoped` lookup. Leaving the club is a soft delete (`active = false`). It's versioned with `@Version` from day one, like `User` (new collection, so no backfill). Jersey numbers are unique among a club's active players via a partial unique index (`Player.JERSEY_NUMBER_INDEX`, filter: `jerseyNumber` is a number and `active` is true) — the index is the guarantee, not a service-level check. Bean Validation on entities (`Player`, `User`) is **not** run on save; only request DTOs are validated, so a write path must validate its input before building the entity. The secondary-≠-primary position rule is `squad.DistinctPositions`, usable on any `squad.HasPositions` (e.g. a request record). The squad API (`squad.PlayerService`) loads a player through the club-scoped `findById` first (another club's → 404), filters lists in memory (never a hand-built `MongoTemplate` query, which would bypass club scoping), maps a `DuplicateKeyException` to a jersey 409 only if its `MongoWriteException` cause names `Player.JERSEY_NUMBER_INDEX` (anything else is rethrown), and on `PUT` compares the client's `version` to the stored one; a mismatch and a save race lost after that check are the same `StalePlayerVersionException` 409 (no retry — it's a multi-field form edit). A released player is read-only until re-activated; re-activation sets the jersey number from its request (null = none, index-checked, no fallback), the only way to change a released player's number. Permanent delete (ADMIN) is deliberately not version-checked — `ClubScopedRepositoryImpl.delete` removes by id + clubId only. Player ages use `Clock.systemDefaultZone()`, the zone of Hibernate Validator's default `ClockProvider` that `@AdultAge` uses. Ages are computed only by `PlayerService.completedYears` (whole years, `Period`) and `PlayerService.exactAge` (fractional, for the summary's average; its whole part is always `completedYears`, so a 29 February birthday falls on 1 March in a non-leap year). `Position.line()` is the only place that maps a position to its `Line`; don't hard-code that mapping anywhere else.

`auth.Club` (the tenant root, `@NotClubScoped`) has **no** `@Version` — adding one would make existing documents look new to Spring Data (a `save` becomes an insert → duplicate key), so it would need a backfill like `UserVersionBackfill`. Its name is changed only by `ClubRepository.updateNameByClubId`, an `@Query`/`@Update` `$set` of `name` alone on the token's clubId — never a load-modify-`save` of the whole document. That method is `void` on purpose: Spring Data returns an `@Update` method's *modified* count (0 for an unchanged name too), so `auth.ClubSettingsService` detects a missing club on the re-read it returns. The name is trimmed (`Club.setName`, `UpdateClubRequest`) and limited by one constant, `Club.NAME_MAX_LENGTH` (100), on both — so the owner bootstrap, which validates the entity, applies the same rule. `ClubResponse` is shared by `/clubs/me` and `/me`'s `club`. When the club gets several settings edited as one form, it must move to `@Version` (+ backfill) and client-sent versions, like `Player`.

Images (player photos, and the club logo — `ImageKind.CLUB_LOGO`, owner id = the clubId itself, code in `auth.ClubLogoController` / `ClubLogoService`, at `/clubs/me/logo` — deliberately not under `/auth`, so the `Path=/auth` refresh cookie isn't sent with it; and staff photos — `ImageKind.STAFF_PHOTO`, owner id = the user id, code in `auth.StaffPhotoController` / `StaffPhotoService`, at `/users/me/photo` and `/users/{id}/photo`, likewise not under `/auth`) go only through `common.ImageStorage` — no method takes a `clubId`, it's read from `ClubContext`. Its only implementation, `common.GridFsImageStorage` (GridFS bucket `images`), is the only GridFS code in the codebase (ArchUnit-enforced: nothing outside `common` may depend on GridFS) and applies the `clubId` itself: every query is built by one helper that adds `metadata.clubId`, since GridFS is a documented bypass of the club-scoped repository layer. Keep the interface free of GridFS / driver types so it can move to S3/R2. Uploads go through `common.ImageValidator` → a `common.ValidatedImage`: the type comes from magic bytes only (JPEG/PNG/WebP, `common.ImageType.detect`), never from the client's `Content-Type` or filename; empty or wrong type → field-scoped `BadRequestException` on `file`, over `squadpulse.images.max-size` (2 MB) → `common.PayloadTooLargeException` (413; the container's `MaxUploadSizeExceededException` gives the same 413). `server.tomcat.max-swallow-size: 20MB` is deliberate and server-wide: it makes an oversize upload get its 413 instead of a connection reset, at the cost that Tomcat may read up to 20MB of any rejected body. A reverse proxy in front of the app (Phase 6) must allow request bodies of at least 3MB (nginx defaults to 1MB) — see README "Deployment notes". Replace semantics: an owner's current image is the latest by `(uploadDate, _id)`; `store` uploads first, then deletes only that owner's files strictly *before* the new one — never "all but mine" — so concurrent uploads leave one, with no transaction. The photo isn't on the `Player` document (no `version` change); likewise a staff photo is never on the `User` document, and no photo operation saves a `User` (nothing to retry). A deactivated user is like a released player: photo readable, `PUT`/`DELETE` → 409 (`auth.DeactivatedUserException`). Users can't be hard-deleted, so staff photo upload has no post-store re-check — a future user hard-delete must delete the photo and add that re-check. `PlayerService.delete` removes the photo **before** the player, so a failure in between leaves a photo-less player that a retry cleans up, never an unreachable orphan file; an upload re-checks that the player still exists after storing and removes its file if not.

Email goes through `common.EmailSender`. Its only implementation, `common.LoggingEmailSender`, logs activation / reset codes in plaintext — local development only; it must be replaced by a real, asynchronous provider before any deployment (Phase 6+).

Frontend (KAN-45): every SPA route lives under `/app` (`/` redirects there; the route table is `src/app/router.tsx`, React Router 8 data router — `createBrowserRouter` + `RouterProvider` from `react-router/dom`, no framework mode), so no SPA URL ever shares a prefix with the backend. Component tests render through `renderWithProviders` (`src/test/render.tsx`: a fresh `QueryClient` with retries off, and a memory router). The backend is mocked with MSW (`src/test/msw/`: `server.ts`, and `handlers.ts` for defaults; a test adds its own with `server.use(...)`, reset after each test). `onUnhandledRequest: "error"`, so a request no handler covers fails the test — never loosen that to make a test pass. MSW stays on 2.x until Vitest's peer range accepts 3; no browser worker (dev runs against the real backend). The SPA calls the backend on its own origin — no CORS, no `/api` prefix. In dev, `frontend/vite.config.ts` proxies the backend's top-level prefixes (`BACKEND_PREFIXES`: `auth`, `squad`, `clubs`, `users`; whole segments only, no path or cookie rewriting, `changeOrigin: false`) to `SQUADPULSE_BACKEND_URL` (default `http://localhost:8080`): a new backend prefix must be added there. `apiUrl(path)` in `src/lib/config.ts` (base from `VITE_API_BASE_URL`, empty by default) is the only place API URLs are built. The backend is called **only** through `src/lib/api` (KAN-46): `apiFetch` / `apiJson` (`client.ts`) for every request (bodies are `json` or `formData`, rebuilt per attempt), and the session's own `login` / `refresh` / `logout` (`session.ts`), all on `send` (`transport.ts`, `credentials: "same-origin"` — never `"include"`). The session is the `AuthSession` interface (token, `status` `unknown | authenticated | unauthenticated`, `subscribe`, `login`, `refresh`, `logout`, `clear`), the one seam a desktop build would swap; its only implementation, `createBrowserSession` (app instance `authSession`, React hook `useSessionStatus`), keeps the access token in a Zustand vanilla store, in memory only — no `persist`, nothing in any storage; screens never touch the store or cookies. Refresh rule: a request **sent with a token** that gets `401` → one shared refresh → resent once with the new token; a second `401` ends the session (`clear`). Public endpoints never get the token: `client.ts`'s `PUBLIC_ENDPOINTS` (exact path, query string ignored) must stay in sync with `SecurityConfig.PUBLIC_ENDPOINTS`. A `401` sent without a token (a public endpoint's wrong password or reset code) never refreshes or resends; `403` / other statuses never refresh. A request whose session ended while it was in flight (token now null) rejects with its `401`, no refresh — that would revive a session ended on purpose. Resending a write is safe because a `401` is decided before any handler acts (security filter, or `ActiveCallerCheck` first). A refresh answered with a 4xx ends the session; a 5xx (the dev proxy's 502 when the backend is down) or a network failure keeps it and just rejects. A session ended (`clear`) while a refresh runs stays ended: a generation counter, bumped by `clear` and at the start of `login`, drops the late token and rejects that refresh's callers with a 401; `logout` waits for a running refresh first, and `login` bumps, then waits for it, then sends (so a late refresh with another user's cookie can't overwrite the new token or cookie; a refresh in another tab racing a login is accepted — login takes no lock). A retry with a token another caller already renewed counts as the one retry (no refresh). `subscribe` fires on status changes only, never on a token renewal. The backend revokes the whole token family when an already-rotated refresh token is presented, so two refreshes must never share a cookie: one in-flight refresh per tab (in the session's closure, never React state — StrictMode-safe), and across tabs the POST runs inside the Web Lock `REFRESH_LOCK_NAME` (fallback without `navigator.locks`: in-tab only); a refresh is never aborted (a caller's `AbortSignal` never reaches it). Accepted residual risk: closing the page mid-refresh can still end the session (the fix would be a server-side grace window). Over plain `http://localhost` Safari drops the `Secure` refresh cookie (verified, Safari 26.5.2), so every refresh there gets a 401: develop in Chrome until the dev server is served over HTTPS (KAN-56). Auth screens and routing (KAN-47): the `/app` route's element is `app/SessionGate`, which renders nothing of `/app` (public or protected) while the status is `unknown` — no login-form or content flash: it runs the app-load bootstrap (`lib/auth/bootstrap.ts`, `startSessionBootstrap()`: one `/auth/refresh` per page load through a module-level memoized promise, never `refresh()` from an effect, so StrictMode and remounts can't send a second; only the retry button resets it) behind the loading screen, and a bootstrap that left the status `unknown` (5xx, no response, malformed 200) shows the server-error screen with retry, **never** the login form (the cookie may be fine). Its children: `app/PublicOnlyRoute`, parent of the public routes `/app/login`, `/app/forgot-password`, `/app/reset-password` (paths in `lib/auth/paths.ts`), which `<Navigate replace>`s a logged-in user to `safeNextPath(next)` — also how a login or the reset's automatic login leaves the form; and `app/RequireAuth`, parent of every protected route incl. `/app/*` not-found (so an unknown `/app` path asks for login first): no session → `/app/login?next=<path+search+hash>` (`withNext`, left out for `/app`), except after an explicit logout (`useLogout()`, `lib/auth/logout.ts`, provided by `RequireAuth`, which tells the two apart) → `/app/login` without `next`; it renders its children only once `/me` has data. App shell (KAN-48): `RequireAuth`'s only child is the pathless layout route `app/AppShell` (the sidebar first in the DOM = the start side, then the content column: the top bar `<header>` with the page's only `<h1>` and the user block, then `<main>`), so it renders only once `/me` has data and never on the public auth screens. Protected routes: `/app` (index, `pages/DashboardPage`, a stub until KAN-51), `/app/squad` (`pages/squad/SquadPage`, the squad table), `/app/squad/new` (`pages/squad/NewPlayerPage`), `/app/squad/:playerId` (`pages/squad/PlayerCardPage`) and `/app/squad/:playerId/edit` (`pages/squad/EditPlayerPage`) — KAN-50, all lazy; the static `new` outranks `:playerId` (tested against the installed React Router), `/app/*` → `NotFoundInShellPage` inside the shell (the top-level `*` keeps the full-page `NotFoundPage`). ## Git & Jira conventions
